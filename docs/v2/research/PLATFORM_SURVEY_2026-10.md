## 2. What the documentation actually says (facts worth keeping)

**NautilusTrader.**
- "Within a node, the core consumes and dispatches messages on a single thread." Components: MessageBus, Cache, DataEngine, ExecutionEngine, RiskEngine, Portfolio. Contexts: Backtest, Sandbox (real-time data, simulated execution) and Live, all on one `NautilusKernel`. https://nautilustrader.io/docs/latest/concepts/architecture/
- Design is "crash-only": release builds abort on panic "allowing an external supervisor to restart the process". Reconciliation aligns cached state with venue reports at startup and runs continuous checks at runtime. "Run one concurrent LiveNode per process." https://nautilustrader.io/docs/latest/concepts/live/
- Backtest simulation modules include "FX rollover and CFD swap behavior"; bar execution is OHLC-sequenced; fill models configure slippage. The backtesting page does not discuss latency and gives no speed benchmark. https://nautilustrader.io/docs/latest/concepts/backtesting/
- The README says the project is under active development with breaking changes possible between releases, a v2 release-candidate line, `develop_v1` receiving only critical security backports until v2 is final, and Python 3.12 to 3.14. https://github.com/nautechsystems/nautilus_trader
- Stable integrations list (18 rows): Binance, Bybit, OKX, Kraken, Coinbase, Deribit, dYdX, Hyperliquid, Interactive Brokers, Databento, Betfair, Polymarket, Tardis and others. **No OANDA or IG.** https://nautilustrader.io/docs/latest/integrations/

**QuantConnect Lean.** The Lean CLI docs list OANDA as the one CFD/forex brokerage: "Enter `Trade` for fxTrade or `Practice` for fxTrade Practice"; CLI use requires a paid-tier organisation. The OANDA plugin README says backtests have no slippage, only Market, Limit and Stop-Market orders are supported, and margin is up to 50x. https://www.quantconnect.com/docs/v2/lean-cli/live-trading/brokerages/cfd-and-forex-brokerages and https://github.com/QuantConnect/Lean.Brokerages.Oanda

**freqtrade.** Backtesting "will never replace running a strategy in dry-run mode"; stoploss is evaluated before ROI within a candle; no slippage; the page does not describe spread modelling. `lookahead-analysis` reruns signals on sliced data and flags indicator and signal differences; `recursive-analysis` varies `startup_candle_count` and compares last-row indicator values. Hyperopt docs cap decimals at three places because finer precision "usually leads to overfitted results" and give no out-of-sample or walk-forward guidance. https://www.freqtrade.io/en/stable/backtesting/ , https://www.freqtrade.io/en/stable/lookahead-analysis/ , https://www.freqtrade.io/en/stable/recursive-analysis/ , https://www.freqtrade.io/en/stable/hyperopt/

**ArcticDB licence (note the inconsistency).** The README says production use "requires a paid for license". The LICENSE file (BSL 1.1) has an Additional Use Grant permitting use except as a "Database Service" and a change date two years after each release to Apache-2.0. These two statements do not obviously agree. Treat as unresolved; get legal advice before depending on it. https://github.com/man-group/arcticdb

## 3. Synthesis

### 3.1 Common architectural patterns, and where Fiboki sits

**Patterns common to serious platforms (verified in the docs above):**
1. One event-driven core shared by backtest and live (Nautilus, Lean, Barter, Lumibot, Blankly, hftbacktest). Fiboki's variant, a paper worker driving the same position book as the backtester, is a stronger form of this than freqtrade's, whose own docs concede backtest assumptions differ from dry-run.
2. Ports-and-adapters for brokers (Nautilus states it; Barter has `ExecutionClient`; Lean has brokerage plugins). Matches your rule.
3. Paper or dry-run as the default state with explicit gating: freqtrade defaults `dry_run` to true, `initial_state` to `stopped`, and `force_entry_enable` to off.
4. Columnar files for market data: Nautilus's `ParquetDataCatalog`, pysystemtrade's Parquet time series, hftbacktest's Parquet intermediates. Your SQLite plus parquet is mainstream. freqtrade also defaults to SQLite for trades.
5. An external supervisor restarts the process (Nautilus crash-only design, freqtrade `docker compose up -d` and systemd watchdog, pysystemtrade cron).
6. A pre-trade risk layer separate from the strategy (Nautilus `RiskEngine`, pysystemtrade trade and position limits, freqtrade protections: StoplossGuard, MaxDrawdown, CooldownPeriod, LowProfitPairs).
7. A chat or command channel for the single operator (freqtrade Telegram with `chat_id` and `authorized_users`; Barter external engine commands).

**Good-unusual choices (Assessment, with the verified comparator in brackets):**
- Strategies as declarative DSL documents. Most platforms use code classes (freqtrade, Lean, Lumibot). The nearest configuration-driven peers are qlib's `qrun` workflows and Hummingbot controllers. A hashable DSL makes audit and holdout registration far easier.
- The 7-rung validation ladder with versioned promotion gates and a one-shot holdout registry. The most comparable published material is the ML4T book's "evidence boundary", walk-forward CV, Deflated Sharpe, Rademacher anti-serum and White's Reality Check. I did not find an open-source trading platform that integrates all of these as an enforced pipeline. Platform docs mostly stop at hyperopt warnings.
- Costs in the backtest: spreads, financing, ESMA/IG leverage caps, GBP account. freqtrade's backtester has no slippage and no documented spread model; Lean's OANDA plugin notes no backtest slippage. Nautilus has FX rollover modules, but the IG/ESMA specifics would be yours to build.
- Five independent controls against live execution, and LLM agents with no execution authority. OctoBot's ChatGPT mode "trades accordingly" and Lumibot agents can be allowed to trade; Hummingbot's Condor is the closer analogue because it routes LLM decisions through deterministic execution.
- Hash-chained append-only ledger. I did not find an equivalent in the READMEs and docs I read (not an exhaustive code search).

**Bad-unusual, or at least risky (Assessment):**
- **Single machine with no rehearsed failover.** pysystemtrade, also single-machine, explicitly recommends a backup machine with current code and data, plus a scheduled failover rehearsal ("stop the live machine running ... start up the backup machine. The live machine then becomes the backup"). Your move to a Mac desktop gives you that second machine for free.
- **Per-bar pandas access and per-bar recomputation of portfolio volatility** in the engine loop (your own profiling). Section 3.5.
- **A bespoke DSL interpreter and engine has a bus-factor cost.** Nobody else maintains it, and every fix must preserve determinism and historical hashes.
- **SQLite with multiple launchd processes.** Fine with WAL mode and short transactions; worth a stress test (I have not inspected your code).
- **Python 3.11 floor.** Not an issue today, but Nautilus now needs 3.12 to 3.14 (verified), so any future adoption forces a runtime bump.

**NautilusTrader in detail (Assessment, building on the verified facts above).**
- *What it would give you:* a mature event kernel, reconciliation, a RiskEngine, a Sandbox mode that maps exactly onto your paper worker, FX rollover and CFD swap simulation modules, a Parquet catalog, and a Rust core.
- *Why it does not pay off for you now:* your strategies are H4 bar strategies (about 330 trades in 20 years). Nautilus's headline strengths (nanosecond data, order books, latency, queue models) are irrelevant at that frequency. Its docs make no speed claim I could verify, so I cannot promise it relieves your bottleneck. The things that make Fiboki distinctive (DSL, ladder, holdout registry, ledger, IG/ESMA realism) all sit outside Nautilus, so you would be maintaining both. There is no OANDA or IG adapter. The API is explicitly unstable until 2.0.
- *What to take:* crash-only design with an external supervisor (launchd `KeepAlive` already provides this); startup reconciliation between local state and venue state; a pre-trade `RiskEngine` check as a separate module from strategies (you already have five controls); the explicit Backtest/Sandbox/Live context vocabulary.
- *Revisit trigger:* if you ever approve live execution at scale, or want tick-level strategies. At that point a time-boxed spike (one DSL seed, one instrument, compare trade lists bar by bar against your engine) would tell you the real parity gap.

It cannot replace anything in your stack, but it is the best source of patterns: pooled estimation (section 3.3), instrument weights with a diversification multiplier, a process-control table, reconciliation locks, and its reports and backup discipline (section 3.4). ### 3.3 Evaluating a strategy across many instruments: pooling, sample size and overfitting

**What pysystemtrade does (verified from `backtesting.md`).**
1. *Pooled forecast scalars.* "Pooled forecast scale estimate (default)", enabled by `pool_instruments=True`. It takes the cross-sectional median of absolute forecast values across instruments and rescales to an average absolute value of 10, using a rolling mean "so always out of sample" with `window` 250000 (effectively expanding) and `min_periods` 500. Carver: "I strongly recommend using pooling, since it's always good to get more data." The one stated exception is a rule whose scale is naturally different across instruments.
2. *Pooled gross returns for forecast weights* (`pool_gross_returns: True`). Pooling applies to forecast weights only, not instrument weights. Carver's blog argues a single instrument rarely has enough data to show one rule beating another with significance (it "can take decades"). His preferred set-up is "half pooling": pooled gross returns, **instrument-specific costs**, with turnover pooled (`use_pooled_turnover: True`) but cost per turnover kept per instrument. A cost ceiling (`ceiling_cost_SR: 0.13` in annual Sharpe units) removes rules too expensive to trade; the blog calls this "very very important". https://qoppac.blogspot.com/2016/05/optimising-weights-with-costs.html
3. *Then a portfolio.* Instrument weights (fixed, or estimated by bootstrapping or handcrafting) and an instrument diversification multiplier combine per-instrument sub-system positions into one portfolio. Correlations used for forecast-weight estimation can be pooled; the IDM estimate cannot (`pool_instruments: True ## not available for IDM estimation`).
4. *Anti-overfitting by design.* Few parameters; fixed or hand-crafted weights as the default (missing forecast scalar defaults to 1.0, missing forecast weights to equal); weekly data for optimisation; fitting period `expanding` (recommended), `rolling`, and "`in sample` (never!)"; and a doc warning to "beware of implicit overfitting!" when iterating. I found no deflated Sharpe, PBO or multiple-testing correction in the docs I read.

**What this means for your pooled-portfolio idea (Assessment).** The idea matches Carver's logic and is the right direction: it raises the evidence available without more history. Three cautions:
- **Pooled trades are not independent trades.** Sixteen FX instruments share a USD factor and other common drivers. For equicorrelated returns with mean pairwise correlation ρ, a rough effective count is N_eff = N / (1 + (N - 1) ρ). Illustration only, using your 330-trade figure and treating it as per-strategy-per-universe: if the 16 instruments had ρ = 0.3, N_eff ≈ 2.9, giving roughly 960 effective trades; at ρ = 0.5, N_eff ≈ 1.9, roughly 620; at ρ = 0.7, N_eff ≈ 1.4, roughly 460. Against MinTRL of 425 that is marginal at high correlation. These numbers are my arithmetic on assumed correlations, not measurements; measure the real correlation of per-trade or per-period P&L from your own data (PCA or the mean off-diagonal of the return correlation matrix on a regular time grid).
- **Evaluate on a regular time grid, not on a pile of trades.** Aggregate the pooled portfolio's P&L to a fixed period (daily or weekly) and compute PSR, MinTRL and DSR there with sample skew and kurtosis, using a stationary block bootstrap for confidence intervals (arch provides the bootstrap and the SPA/StepM machinery, source verified). That sidesteps the correlated-trade problem and makes the unit of evidence match the unit of deployment.
- **Pooling changes the null and the trial count.** You are now testing "this strategy has an edge on average across the universe", not "on EURUSD". Choosing the universe after looking at results is a trial. Report heterogeneity (leave-one-instrument-out, share of instruments with positive contribution) so a few instruments cannot carry the pool, and keep per-instrument spreads and financing in the pooled run exactly as Carver keeps per-instrument costs in half pooling.
- Your ladder's DSR, PBO, SPA and StepM stages should run over the number of *portfolio candidates* you actually tried, which pooling reduces (fewer, better-evidenced candidates), a side benefit.

**What others do about sample size and overfitting (verified unless stated).** freqtrade: caps parameter precision, offers lookahead and recursive-indicator checks, but no out-of-sample guidance in the hyperopt page. Jesse: trade-order shuffling and candle-based Monte Carlo. quantstats: Monte Carlo on returns. ML4T: an evidence boundary, walk-forward CV, Deflated Sharpe, Rademacher anti-serum, White's Reality Check, and a retrain/pause/retire feedback loop. mlfinlab (closed): "Backtest Overfitting Tools", purged CV. qlib: rolling retraining. skfolio: combinatorial purged CV. arch: SPA, StepM, MCS, RealityCheck. Assessment: your ladder is more complete than any open-source platform pipeline I surveyed; the gap is sample size, not method.

### 3.4 How single-operator production systems are run, and what to copy

**pysystemtrade (verified from `production.md` and `dashboard_and_monitor.md`).**
- *Scheduling:* a "hybrid of Python and cron". Cron launches `run_*` processes daily; the built-in scheduler records start, stop and PID, enforces a start and stop window, requires a named previous process to have run in the last 24 hours, and lets the operator set STOP, GO or NO RUN per process or globally ("emergency shutdown"). Carver notes "it's probably better to have trading processes shutting down each night and then restarting in the morning, than trying to keep them running continuously".
- *Crash handling:* the startup script marks all processes closed and clears broker client IDs; the monitor or dashboard detects dead PIDs, emails, and marks them closed but "will not automatically respawn the processes". Crash-recovery checklist: switch cron off, check the database, run the full report set (especially status and reconcile), repopulate the order stack, switch cron back on.
- *Reconciliation:* the stack handler compares broker and database positions at contract level; a mismatch **locks the instrument** until it clears or the operator intervenes. A reconcile report exists. Fills missed while down must sometimes be entered by hand.
- *Monitoring and alerts:* daily emailed reports (roll, P&L, status, trade, reconcile, strategy, risk, liquidity, costs); critical log lines email; price spikes email and require a manual check; a more-than-10% jump in account value is not applied to capital until the operator confirms.
- *Logging:* a socket server serialises writes from many processes into one rotating log (five days by default); stdout "echo" files retained for 30 days by default.
- *Backups:* daily `mongodump`; a CSV export of most tables "as I am super paranoid"; `rsync` of Parquet; a backup machine kept current; a rehearsed failover. The docs say what the CSV export misses (roll status, trade and position limits, overrides, logs).
- *Deployment simplicity:* one local Linux machine, MongoDB, cron. Cloud is optional, not assumed.

**freqtrade (verified).** `docker compose up -d` (not `run`) so the container restarts after reboot; live mode needs a fresh database; UI on port 8080 reached through an SSH tunnel or VPN because FreqUI "does not support https out of the box", with a random `jwt_secret_key` strongly recommended; systemd user service with an optional `sd_notify` watchdog (not available inside Docker); rotating file logs (10 MB by default, 10 backups) and syslog or journald; secrets via `FREQTRADE__` environment variables, which override the config file; Telegram with `chat_id` and `authorized_users` (an empty list means nobody can control the bot), `/pause` (not persisted across restart), `/forceexit`, `/reload_config`, `/logs`, and per-event notification levels; `/stopentry`-style pause as the safe halt.

**What I would copy (Assessment, ranked by value for effort).**
1. **A dead-man's switch.** launchd `KeepAlive` restarts a crashed worker but does not tell you a worker is alive and doing useful work. Have the paper worker ping a heartbeat URL after each successful bar cycle (Healthchecks, BSD-3-Clause, can be self-hosted) and alert on silence. Add a push channel (ntfy, Apache-2.0, or Telegram as freqtrade does).
2. **A process-control table** with start and stop windows, previous-process preconditions and a global STOP, as pysystemtrade does. Cheap to add to SQLite and it makes the "five independent controls" operable.
3. **Data reconciliation analogues.** Because OANDA is read-only, reconcile what you *can*: candle completeness against the broker's calendar, price-spike flags that email and pause (Carver's price-spike pattern), and a daily state-hash comparison between the paper book and a replay of the ledger.
4. **Backups with a tested restore.** SQLite online backup or Litestream (Apache-2.0) plus an off-box copy of parquet and the ledger, and a quarterly restore drill onto the second Mac. Carver's CSV-export idea suits your hash-chained ledger: export it as plain text so it survives a database fault.
5. **Rehearsed failover** between the MacBook and the desktop, as Carver does at weekends.
6. **Two freqtrade invariants as CI tests:** a *truncation test* (signals at bar t computed on data truncated at t equal those computed on the full series) and a *warm-up sensitivity test* (indicator values at a fixed bar stable as the history length is varied). These catch look-ahead and recursive-indicator drift without any infrastructure. Check whether your suite already has them.
7. **Platform hygiene specific to macOS (Assessment, not from the docs):** stop idle sleep for the worker, use a UPS on the desktop, and make the worker tolerate missed bars after a sleep by catching up rather than assuming continuity.

### 3.5 Engine-speed techniques and what applies to your hot spots

Your profile: about 500 core-seconds per 60 backtests (8.3 s per backtest), with per-bar realised portfolio volatility and per-bar pandas column access as hot spots. For scale (Assessment, assumption stated): H4 FX is roughly 6 bars a day, about 1,560 bars a year, so about 31,000 bars over 20 years; across 16 instruments that is about 500,000 bar-steps per backtest. If a backtest covers all of those, 8.3 s means roughly 16 microseconds per bar-step, which is slow for compiled code but typical of pandas scalar access. Check this against your actual bar counts.

| Technique | Seen in | Applies to your hot spots? | Determinism notes |
|---|---|---|---|
| Convert DataFrames to NumPy arrays once, then index by integer position in the loop | Universal practice; Numba kernels (hftbacktest, vectorbt) | **Yes, first and cheapest.** Fixes the per-bar column access | Fully deterministic; same arithmetic |
| Compute realised portfolio volatility incrementally (rolling or exponentially weighted updates in O(1) per bar) instead of recomputing a window each bar | Standard engineering (Assessment) | **Yes.** Positions make it path-dependent, so it cannot be vectorised away, but it can be updated incrementally | Floating-point summation order differs from a window recompute; pick one definition, fix the order, add golden tests, and document the tolerance. Consider periodic exact recomputation if drift matters |
| Numba `@njit` kernel for the bar loop, cached | hftbacktest uses `@njit` throughout; vectorbt uses Numba on the hot path | **Yes**, after the array conversion | Use `fastmath=False`: the Numba docs say that without it the loop "must accumulate in strict order", while with it "floating point reassociation is permitted". Avoid `parallel=True` inside one backtest: with `prange`, "each thread computes a partial sum", so reduction order and rounding can vary run to run. Parallelise **across** backtests (process pool) instead; each run stays sequential and bit-reproducible |
| Precompute fill conditions or signals in bulk, then run a minimal stateful pass | hftbacktest "accelerated backtesting" (its page quotes a full backtest of 1 min 49 s against roughly 0.4 to 0.6 s accelerated, noting results differ in detail and recommending validation against the full run) | **Partly.** Signals and indicators can be vectorised and cached by (instrument, parameter hash); the portfolio pass stays sequential | Safe if the accelerated path is proven identical on your golden set. Unlike hftbacktest's variant, do not drop modelled costs |
| Cache indicator and feature arrays keyed by content hash | freqtrade caches backtest results by strategy and config (and warns it can miss changes in imported modules) | **Yes** for the validation ladder, which re-evaluates the same instrument data across many parameter sets | Key on the DSL hash plus data hash plus code version to avoid freqtrade's stale-cache trap |
| Polars for data preparation | polars is MIT, 39,917 stars, PyPI 2.0.0 released 6 Oct 2026 | Only for loading and feature tables; **not** for the per-bar stateful loop | Pin the version (2.0.0 is days old); set explicit ordering where group order matters |
| Rust core via PyO3 | Nautilus, Barter, hftbacktest (Rust edition) | Possible for the position book and volatility kernel, but a language and toolchain cost for one maintainer | Deterministic if integer or fixed-point arithmetic is used (Nautilus offers 128-bit high-precision and 64-bit standard modes); not needed if Numba reaches your target |
| Batch parameter broadcasting | vectorbt | Weak fit: your rule set is a path-dependent portfolio with margin, caps and financing | Vectorbt's README does not discuss path-dependent portfolio-level risk; PRO-only features include leverage and limit orders (as listed in the README) |

Suggested order (Assessment): arrays first (days), then incremental volatility (days), then a Numba kernel behind a feature flag with a bit-for-bit golden test comparing trade lists and equity to the current engine, then process-level parallelism across backtests. I would expect one to two orders of magnitude, but that is an estimate until profiled on your code.

### 3.6 Ranked recommendation

1. **Keep as is: the architecture, DSL, ladder, holdout registry, ledger, execution controls and local-first deployment.** Reasons: it is differentiated from, and more rigorous than, everything surveyed on validation and cost realism; the nearest replacement (Nautilus) solves problems you do not have (tick-level, latency, many venues) while leaving your real ones (sample size, engine speed, single-machine resilience) untouched and adding re-baselining risk. Effort: none.
2. **Adopt patterns, not packages (highest return).**
   - a. Engine speed: arrays, incremental volatility, Numba kernel, parallelism across runs. Effort: roughly 1 to 3 weeks including golden tests (Assessment).
   - b. Pooled-portfolio evaluation with a regular-grid unit of evidence, effective-N correction, heterogeneity reporting and "half pooling" of costs. Effort: roughly 1 to 2 weeks (Assessment).
   - c. Operations: heartbeat and push alerting, process-control table, backup and restore drill, failover rehearsal, truncation and warm-up tests. Effort: roughly 3 to 5 days (Assessment).
3. **Adopt specific small components (optional, low risk):** Healthchecks (or any heartbeat service), ntfy or Telegram, Litestream or equivalent backups, skfolio `CombinatorialPurgedCV` and arch `SPA`/`StepM` as independent cross-checks of your own implementations, polars for data preparation only.
4. **Do not adopt:** Lean, backtrader, blankly, the OANDA wrapper libraries (dormant; plain HTTP to the v20 REST endpoints is simpler), ArcticDB (licence ambiguity, no problem solved), mlfinlab and StockSharp (proprietary), anything AGPL or GPL if the product may be commercialised.
5. **Revisit later:** NautilusTrader (or Lean's OANDA plugin) only if live execution is approved or tick-level work begins; do a one-seed parity spike first.
6. **Rebuild:** not warranted.
